## 1. 门禁语义（VERIFIED，仓库侧）

`scripts/monitor-staging.sh:129`：

```bash
if (( used_percent > max_disk_used_percent || available_kib < min_disk_available_kib )); then
```

- `max_disk_used_percent=85`（严格大于才失败，**85 本身通过**）
- `min_disk_available_kib=$((5 * 1024 * 1024))` = 5,242,880 KiB = 5 GiB
  （严格小于才失败，**恰好 5 GiB 通过**）

`scripts/recover-staging.sh:175` 是同一门槛的另一种写法：
`(( used <= 85 && available >= 5242880 ))`。两者等价。

**硬门槛**：`Used% ≤ 85` 且 `Available ≥ 5 GiB`。
**建议目标**：见第 5 节——不能只做到"刚好 85%"。

### 1.1 三个独立的容量检查点

monitor 依次检查（`scripts/monitor-staging.sh:454,466,473`）：

1. `host-capacity`：根文件系统；
2. `docker-capacity`：`asteria-drive-staging-app-secrets` 卷所在文件系统
   （在本 compose 里 Docker 数据目录默认为 `/var/lib/docker`，通常与根同盘）；
3. `data-volume-capacity`：`asteria-drive-staging-postgres-data` 与
   `asteria-drive-staging-seaweedfs-data` 两个卷。

当前失败停在 **第 1 个**，因此第 2、3 个检查点的结果仍 UNKNOWN。
**关键推论**：如果 Docker 数据目录与根同盘（`docker_data_root_on_root_filesystem`
会记录这一点），那么释放根盘空间**同时**改善第 2、3 个检查点；如果不同盘，
清理根盘对它们**没有帮助**——这必须在 P1 取证中确认。

**第 1 步（不可逆性最低）**：C2 Build Cache + C6 journal 轮转 + C7 apt 缓存。

**第 2 步（需确认引用关系）**：C1 未使用镜像。删除前必须列举"哪些镜像被至少一个

## 5. 余量建议（硬门槛 vs 建议目标）

**硬门槛**（门禁本身）：`Used% ≤ 85` 且 `Available ≥ 5 GiB`。

**为什么不能只到 85%**：

1. 85% 是**严格大于**才失败，因此 85.0% 通过、85.1% 失败——余量为零。
2. 观测到的日波动约 1 GiB（5.28→5.40 GiB 之间），按 39 GiB 总量折算约 2.5–3%。
3. 一次 PostgreSQL 恢复演练的备份上限是 512 MiB（`max_archive_bytes`），
   演练本身会在 `/tmp` 下产生额外写入。

**建议目标**（供审批时讨论，不是新阈值）：

| 目标 | Used% | Available | 含义 |
| --- | --- | --- | --- |
| 硬门槛 | ≤ 85% | ≥ 5 GiB | 刚好通过，无缓冲 |
| 建议目标 A | ≤ 80% | ≥ 7.5 GiB | 覆盖约 2 次日波动 + 一次演练备份 |
| 建议目标 B | ≤ 75% | ≥ 9.5 GiB | 覆盖更长时间不干预 |

按 39 GiB 总量折算，从 86% 降到 80% 约需释放 2.3 GiB；降到 75% 约需 4.3 GiB。
**这两个数字是估算，误差 ±10%**，以 P1 实测为准。

**本轮不新增也不修改任何阈值。** 上表只是把"清理到多少"变成一个可审批的数字，
而不是把门禁调低。

## 9. 失败处理与回滚

| 失败场景 | 处理 |
| --- | --- |
| 清理后 `Used%` 仍 > 目标 | 停止，不追加删除；重新取证后另立方案 |
| 误删镜像导致容器无法重建 | 从固定 digest 重新拉取（`docker pull ghcr.io/...@sha256:...`），**不修改** compose 摘要 |
| 误删卷 | **不可恢复**；从备份恢复，需独立审批 |
| 清理期间主机负载过高 | 中止 `du`/删除，等下一窗口 |
| 清理后容器不健康 | 不重启、不回滚，先取证再决策 |

回滚的本质是"恢复到清理前状态"，而对镜像/缓存/日志的删除**没有回滚**。
这正是把 C1–C7 与 C8–C10 严格分开的原因：只有后者才需要回滚能力，
而它们本来就不在清理集合里。

## 10. 为什么不会损坏 PostgreSQL / SeaweedFS

| 动作 | 为什么不影响业务数据 |
| --- | --- |
| 删除未使用镜像 | 镜像层与卷是两套存储；卷不在 `overlay2` 中被镜像引用 |
| 清空 Build Cache | BuildKit 缓存与运行中容器的可写层无关 |
| 轮转 journal | 系统日志与应用数据目录无关 |
| 清理 apt 缓存 | 与容器无关 |
| 删除容器 json-file 日志 | 只删日志文件本身；Docker 在容器运行时会重新打开该文件，需用 `truncate` 而非 `rm` |

**注意**：对运行中容器的日志文件应使用 `truncate -s 0`，而不是 `rm`——
后者会让 Docker 继续写入一个已删除的 inode，空间不会释放。
