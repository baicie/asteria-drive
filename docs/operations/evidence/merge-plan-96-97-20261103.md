## 2. 合并策略

仓库同时允许 merge commit、squash 与 rebase merge，但历史以 merge commit 为主
（`Merge pull request #85/#90/#91/#95`）。

**推荐：两次都使用 “Create a merge commit”。**

理由：

1. #96 合并后，`15cd5f5` 进入 main 的历史，GitHub 自动把 #97 的 merge base 识别为
   `15cd5f5`；PR #97 的 diff 只剩 14 个独立增量提交，不会重复显示 #96 内容。
2. 保留 4 + 14 个原始提交与堆叠关系，便于回滚与审计。
3. 与仓库现有历史一致，不需要重写任何已审查的 SHA。

**若采用 Squash：** #96 会生成一个新的 squash commit `S96`（树等于 `15cd5f5` 的树，但
`15cd5f5` 不在 main 历史中）。此时 #97 的 merge base 会退回 `fb0e5e0`，PR #97 会重新
包含 #96 的全部改动。必须先把 #97 的独立增量重放到新 main 上：

```bash
git fetch origin
git switch claude/web-transfer-reliability-8ace5b
# 只重放 15cd5f5 之后的 14 个提交
git rebase --onto origin/main 15cd5f5476088641d1d6a66b34c6982c80f46356
# 预期无冲突：S96 的树与 15cd5f5 相同
git push --force-with-lease origin claude/web-transfer-reliability-8ace5b
```

重放后必须确认 `origin/main..HEAD` 只剩独立增量、`git diff --stat origin/main...HEAD`
不再包含 #96 的文件（如 `web/package-lock.json`、`web/src/features/downloads/*`），并等待
新 HEAD 的 CI/Security 全绿后再合并 #97。

**禁止：**

- 用 GitHub “Update branch” 把 main 合入 #97：会产生一个包含 #96 内容的 merge commit，
  使 #97 diff 继续膨胀。
- 对 #96 使用 Rebase merge：4 个提交在 main 上换新 SHA，但 `15cd5f5` 不会成为 main 祖先，
  #97 仍需上述重放；收益为零且改写历史。
- 颠倒顺序合并 #97 再合并 #96： #97 已包含 #96 全部内容，#96 将无独立差异。
