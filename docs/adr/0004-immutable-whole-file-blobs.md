# ADR-0004: 不可变整文件 Blob、路径与 Key 解耦及内部版本

- 状态：Accepted
- 日期：2026-08-02
- 范围：文件 Namespace、版本与对象布局

## Context

用户路径会频繁重命名、移动、覆盖和恢复，而对象存储中的大对象复制成本高且不具备目录事务。若路径直接成为对象 Key，每次 Namespace 变化都可能触发复制、缓存失效和并发冲突。MVP 若立即采用内容定义分块和全局去重，则会显著增加对象数量、Manifest 拼装、隐私证明和垃圾回收复杂度。

## Decision

MVP 以“一个文件版本对应一个不可变整文件 Blob”为默认模型，并分离三个概念：

- `file_node` 表示租户 Namespace 中可见的文件或目录，保存父节点、规格化名称和当前版本引用。
- `file_version` 是只追加的内部版本记录，引用一个 Blob；每次上传或覆盖都创建新版本。
- `blob` 描述对象存储位置、大小、Checksum、状态和生命周期，不包含用户路径语义。

对象 Key 使用服务端生成的、不透明且稳定的标识，例如租户作用域下的 Blob ID；不得使用完整用户路径，不得接受客户端自选 Key。重命名和移动仅在 PostgreSQL 事务中修改 Namespace。覆盖文件先创建新 Blob 和 `file_version`，再原子更新 `file_node.current_version_id`，绝不原地覆盖已提交对象。

即使 MVP UI 暂不开放历史版本，每次成功提交仍建立内部版本记录，避免日后改变基本存储语义。删除节点或版本只移除逻辑引用；物理 Blob 在保留期结束且确认无有效引用后由 GC 异步删除。内容 Hash 用于完整性校验和租户内的未来秒传候选，不能单凭 Hash 授予对既有内容的访问。

## Consequences

- 重命名、移动、分享和恢复主要是元数据操作，不复制文件内容。
- 已提交对象可安全缓存并支持 Range，版本切换只改变引用。
- 覆盖会产生额外存储占用，需要回收站、保留策略和可靠 GC。
- Namespace 与对象存储清单不再一一对应，所有用户目录查询必须走 PostgreSQL。
- 整文件版本之间默认不做块级去重，大型文件小改动仍需上传新对象。

## Rejected alternatives

- **把完整路径作为对象 Key**：重命名和移动会变成昂贵复制，且路径并发与对象存储语义不匹配。
- **原地覆盖同一对象**：破坏不可变缓存、历史版本、并发提交和故障恢复边界。
- **第一阶段全面采用分块 CAS**：对象、Manifest、隐私、加密和 GC 复杂度超出 MVP 收益。
- **跨租户仅凭 Hash 秒传**：会泄露内容存在性并绕过内容占有证明。

## Follow-up or triggers

- 在 DDL 中落实租户作用域、同目录规格化名称唯一约束、版本外键和 Keyset Pagination 索引。
- 定义 Blob 生命周期、回收站保留期、引用校验和元数据/对象联合恢复流程。
- 当桌面同步的大文件小改动带宽成为已测量瓶颈时，再为 FastCDC、Manifest、租户内块级去重和小块 Pack 提出独立 ADR。
