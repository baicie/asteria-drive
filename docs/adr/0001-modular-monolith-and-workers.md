# ADR-0001: 模块化单体与 Worker 演进边界

- 状态：Accepted
- 日期：2026-08-02
- 范围：MVP 服务端部署与代码边界

> 实施注记（2026-08-02）：模块化单体、HTTP 服务和优雅停止已进入候选实现；同进程维护循环尚未
> 实现。其 MVP 阶段要求由 [ADR-0008](0008-mvp-staged-reliability-boundary.md) 修订。

## Context

MVP 需要在小团队条件下尽快交付租户边界、目录、内部版本、上传、下载和回收站等强相关能力。这些操作会共同修改元数据，过早拆成微服务会引入跨服务事务、协议演进和运维成本。另一方面，上传过期和垃圾回收是耗时或可重试任务，不应阻塞 HTTP 请求；后续的预览、扫描、索引和通知也需要独立资源边界。

本 ADR 起草时仓库只有 Go HTTP 服务及少量内存态接口骨架；该历史背景不代表当前实现进度。

## Decision

MVP 使用一个 Go 代码库、一个部署单元的模块化单体：

- `asteria-server` 提供控制面 HTTP API，负责 trusted-dev 身份边界、租户隔离、请求校验和短事务编排。
- 同进程维护循环只执行上传过期、保守孤儿清理和回收站清理，并有独立开关、租约、批次和停止生命周期。

单体内部按业务能力划分 `identity`、`tenant`、`namespace`、`version`、`upload`、`download`、`recycle` 和 `storage` 等模块。模块通过应用服务或显式 port 协作，不跨模块直接操作对方的表或内部类型。HTTP handler 只做协议适配，事务边界位于应用服务。

包边界和任务接口要允许 M2 增加 `asteria-worker`，但独立 Worker、Outbox、预览、扫描、索引和通知不是本轮构建或启动依赖。引入它们时必须先补充事件契约、至少一次投递和运维门禁，不能仅把同进程函数搬到新进程。

## Consequences

- 强相关元数据可在一个 PostgreSQL 事务中保持一致，开发、测试和本地运行更简单。
- 当前部署简单；维护循环的并发和数据库连接仍需限额，避免影响 API。
- 模块边界需要通过包依赖检查、评审和测试维持；模块化单体不会自动阻止耦合。
- 单个 API 发布仍会携带全部核心模块，某些模块尚不能独立发布。
- 维护任务必须幂等；未来独立 Worker 还必须按至少一次投递设计，不能假设“只执行一次”。

## Rejected alternatives

- **MVP 即拆成大量微服务**：强一致操作会被迫使用补偿或分布式事务，团队和运维成本高于当前收益。
- **在 HTTP 请求内同步执行维护任务**：会让请求延迟和外部依赖故障耦合；同进程不等于同步请求路径。
- **无模块边界的单一包结构**：短期代码少，但会使后续拆分、测试和所有权划分失去可靠边界。

## Follow-up or triggers

- 在实现前补充模块依赖图、进程启动方式、优雅停机和维护任务重试规范。
- 当某模块需要独立扩缩容、已有稳定数据边界和负责人、发布节奏成为瓶颈，或故障持续影响整个单体时，再提出拆服务 ADR。
- 优先候选是预览、搜索、扫描和上传编排；Namespace 与版本在事务边界稳定前保持在核心单体内。
