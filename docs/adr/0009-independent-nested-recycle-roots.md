# ADR-0009: 嵌套回收项保持独立回收根

- 状态：Accepted
- 日期：2026-08-02
- 范围：目录回收、恢复与永久清理的子树归属

## Context

目录树允许用户先回收子项，再回收它的祖先。如果第二次回收把所有后代的 `trashed_root_id` 都改成
祖先 ID，原先独立回收的子项会被祖先恢复或清理错误接管。恢复祖先后，该子项可能继续保持
`trashed`，却不再是可列出、可恢复的回收根，形成不可见孤立节点。

回收站需要一个持久且可重试的子树归属规则。这个规则必须同时适用于内存 fake 和 PostgreSQL，且不能
依赖恢复时重新遍历当前父子关系猜测历史操作顺序。

## Decision

1. 每次回收操作只捕获操作开始时仍处于活动 Namespace 的目标节点和活动后代。
2. 回收根保存 `status=trashed`、`trashed_root_id=self`、`original_parent_id` 和 `deleted_at`；被捕获的
   活动后代保留自身节点状态，但保存相同的 `trashed_root_id`，因此对普通查询不可见。
3. 已经属于其他回收根的节点不被祖先后续回收接管。它们的 `trashed_root_id`、原父目录和删除时间保持
   不变，并继续作为独立回收站项列出。
4. 恢复与永久清理严格按持久化的 `trashed_root_id = requested_root_id` 选择成员，不按当前父子关系递归
   扩大范围。
5. 恢复祖先不会恢复独立回收的子项。祖先恢复后，子项可再按自己的回收根恢复到原父目录；若原父目录
   仍不可用，则返回 `restore_conflict`。

## Consequences

- 回收操作顺序不会改变既有回收项的所有权，恢复和清理可以幂等重试。
- 一棵物理父子树中可以同时存在多个回收根；回收站分页按根项列出，而不是按当前树折叠。
- PostgreSQL 回收递归查询必须只沿活动且尚未带回收根的节点继续，内存 fake 必须采用相同筛选规则。
- 清理祖先时可能保留一个独立回收的子树及其 Blob 引用；这是引用安全所要求的行为，不是泄漏。

## Rejected alternatives

- **祖先回收覆盖全部后代归属**：会让先回收的子项失去可恢复入口，并使清理范围取决于操作顺序。
- **恢复时重新递归当前父子树**：当前树不能可靠表达历史回收边界，并可能跨回收根恢复或删除节点。
- **禁止回收含已回收后代的祖先**：把可确定处理的状态暴露为用户操作限制，且不利于批量目录管理。

## Verification

- 内存 Repository 和 PostgreSQL Repository 运行相同场景：回收 child，回收 parent，确认两个根同时
  可见；恢复 parent 后 child 仍在回收站；再恢复 child 后父子关系恢复且回收站为空。
- 永久清理和 Blob 引用保护继续只处理指定 `trashed_root_id` 的成员。
