# ADR-0003: PostgreSQL 真相源、Redis 边界与事件演进

- 状态：Accepted
- 日期：2026-08-02
- 范围：元数据持久化、缓存与事件可靠性

## Context

文件 Namespace、版本、Blob、上传会话与回收状态需要事务一致性和可恢复备份。Redis 适合低延迟临时状态，但持久性和事务模型不应承担最终业务状态。未来增加跨进程异步派生能力时，数据库提交与消息发布还需要避免不可靠双写。

## Decision

PostgreSQL 是 MVP 租户、Namespace、文件版本、Blob 引用、上传会话最终状态和回收站的唯一真相源。所有影响这些数据的正确性判断都必须能在 PostgreSQL 和对象存储事实基础上重建。M2 的正式身份映射、配额、ACL、分享、审计和 Outbox 也遵守同一原则。

Redis 仅用于可丢失、可过期、可从真相源重建的状态，例如：

- 热点读取缓存和短期下载授权缓存；
- 限流计数、短期 Session 和上传临时提示；
- 非关键的互斥或租约加速。

Redis 失效可以造成降级或性能下降，但不得造成文件、权限或已提交版本丢失。关键并发正确性使用 PostgreSQL 唯一约束、条件更新和事务保证，Redis 锁不能成为唯一防线。

本轮 MVP 没有跨进程事件消费者，因此不创建占位 Outbox，也不把 Redis、Kafka 或 Redpanda 变成运行依赖。需要第一个可靠异步消费者时，M2 必须在业务事务中写入 `event_outbox`，由 Worker 按至少一次语义认领；消费者使用事件 ID 或业务幂等键去重。本决策不宣称端到端 exactly-once。只有当轮询吞吐、消费者数量或回放需求超出 PostgreSQL Outbox 能力时，才评审 Kafka/Redpanda。

## Consequences

- MVP 元数据不依赖缓存或消息系统即可恢复；引入第一个异步消费者时需要先落地 Outbox。
- PostgreSQL 的容量规划、索引、PITR、WAL 归档和恢复演练成为核心运维责任。
- Redis 可独立扩容或清空，但应用必须具备缓存击穿保护和数据库降级策略。
- M2 的至少一次投递会产生重复事件，所有外部副作用都需要幂等键或去重记录。

## Rejected alternatives

- **Redis 保存最终文件或配额状态**：缓存丢失、淘汰或复制异常会破坏业务事实。
- **先提交数据库再直接发布消息**：进程可在两步之间崩溃，导致永久漏事件。
- **先发布消息再提交数据库**：消费者可能观察到尚未提交或最终回滚的数据。
- **MVP 强制引入 Kafka/Redpanda**：当前规模尚不能抵消额外部署和故障排查成本。

## Follow-up or triggers

- 补充 PostgreSQL schema、事务隔离级别和备份恢复策略。
- 引入第一个跨进程异步消费者前，补充 Outbox schema、认领 SQL、重试/清理策略，以及“数据库已提交、进程崩溃、重复投递、消费者失败”故障测试。
- 当轮询延迟、事件吞吐、多消费者回放或跨系统集成超出 PostgreSQL Outbox 能力时，评审 Kafka/Redpanda 引入方案。
